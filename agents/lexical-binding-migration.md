# Agent: lexical-binding migration

A focused fix agent that adds the `lexical-binding: t` file-local cookie to
Emacs Lisp files that lack it, but only where the change preserves behaviour.

## Goal

Bring files that compile under dynamic binding onto lexical binding, which is
faster, catches more mistakes, and is expected by modern Emacs. One package per
run, one pull request.

## Inputs

- A package name and its upstream repository URL (GitHub, no FSF assignment).

## Process

1. Identify files whose first line lacks a `lexical-binding` cookie.
2. For each, determine whether the file relies on dynamic binding: look for a
   `let`/`let*`-bound variable that a called function or macro reads via
   `boundp`, `symbol-value`, or `special-variable-p`, or that an
   `evil-define-key` / single-arg `eval` / similar macro resolves dynamically.
   If it does, LEAVE the file (record it as residual). Adding the cookie there
   would change behaviour.
3. For a file that does not rely on dynamic binding, add
   `;; -*- lexical-binding: t; -*-` to the first line, then silence any
   newly-surfaced warnings behaviour-preservingly: underscore unused arguments,
   and for variables generated by the package's own anaphoric macros add a
   no-op `(ignore VAR ...)` inside the macro body where that does not contradict
   the macro's documented contract.
4. Verify: byte-compile with warnings treated as errors; confirm no new
   warnings and that tests still pass; check balanced parens.
5. Add or extend CI to byte-compile with warnings as errors on the minimum
   supported Emacs and the latest stable; commit the cookie additions and the
   CI change separately; get the fork CI green; open one pull request that lists
   the migrated files and any left as residual with reasons.

## Hard rule

Behaviour preservation is the requirement. A `lexical-binding` cookie is not a
no-op: only add it where the file's bindings are all lexical in effect already.
When in doubt, leave the file and record why.
